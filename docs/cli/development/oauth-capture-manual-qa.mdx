---
title: "OAuth Capture Manual QA"
description: "Manual witness checks for declarative OAuth capture providers."
---

Declarative OAuth capture has unit coverage for parsing, response rewriting,
phantom resolution, persistence, and fail-closed HTTP/2 behavior. Real agent
logins are manual QA because they require live accounts, browser/device auth,
and provider-specific service availability.

Do not paste real token values into issues, logs, or chat. The useful evidence
is shape and routing:

- token endpoint paths are matched by OAuth capture
- token responses are rewritten to phantoms
- persisted auth files contain only phantom or synthetic JWT-shaped values
- normal agent API calls resolve phantoms only through the admitted proxy route
- denied Keychain or credential-store access does not prevent phantom-backed use

## macOS Keychain persistence

On macOS, captured real OAuth tokens persist to an ACL-restricted macOS
Keychain item instead of `~/.local/state/nono/oauth-capture/providers.json`.
The ACL trusts only the `nono` binary at the path it was saved from, so
reading the item from any other process (including a bare `security` CLI
invocation) triggers a system Allow/Deny dialog rather than a silent read —
that dialog is the protection working, not a bug.

After a login capture on macOS:

- confirm `~/.local/state/nono/oauth-capture/providers.json` was **not**
  created (macOS never writes this file)
- from a separate terminal, run:

  ```sh
  security find-generic-password -s nono -a oauth_capture_store -w
  ```

  Expect either a system Allow/Deny dialog or a denial — a real token value
  printed without a prompt would indicate the ACL is not restrictive enough
- kill and restart the `nono run` session against the same profile and
  confirm the previously captured phantom still resolves (`resolved OAuth
  phantom token for admitted consumer`), proving persistence survived the
  restart via Keychain rather than the file backend

## Configuring the persistence backend

The backend is chosen by the managed, profile-wide scalar
`oauth_capture_store_backend`. The default is `auto` (macOS Keychain on macOS,
the `providers.json` file backend elsewhere). Set it to `file` to force the
file backend on every platform, including macOS, or `keychain` to force the
Keychain backend (which resolves to the file backend off macOS).

### Option A — macOS Keychain (default)

Enabling an `oauth_capture` provider is enough to turn persistence on; on macOS
it routes to the ACL-restricted Keychain automatically. Because the Keychain
backend also derives a `security` mediation, the profile **must** define a
`security` command policy with a session sandbox — otherwise resolution fails
closed (see [Errors](#errors) below).

```jsonc
{
  // "auto" is the default; shown here for clarity. Omit for the same behaviour.
  "oauth_capture_store_backend": "auto",

  "credential_providers": {
    "codex": {
      "type": "oauth_capture",
      "token_endpoints": [
        {
          "host": "https://auth.openai.com",
          "path": "/oauth/token",
          "response_fields": [
            { "path": "access_token",  "kind": "opaque" },
            { "path": "refresh_token", "kind": "opaque" }
          ]
        }
      ]
    }
  },

  // Required when the Keychain backend is active. Give `security` a session
  // sandbox permissive enough for your agent's normal `security` usage; nono
  // auto-prepends a deny intercept for the oauth_capture_store account, so you
  // never write that rule yourself. The fs_read below is illustrative — scope
  // it to what your agent legitimately needs from `security`.
  "command_policies": {
    "commands": {
      "security": {
        "sandbox": {
          "fs_read": ["~/Library/Keychains"]
        }
      }
    }
  }
}
```

The item lands under service `nono`, account `oauth_capture_store`;
`~/.local/state/nono/oauth-capture/providers.json` is never written.

### Option B — plaintext `providers.json` (opt out of the Keychain)

For headless/SSH hosts, or anyone who does not want the store in the login
keychain. No `security` policy is needed — the mediation is not derived for the
file backend.

```jsonc
{
  "oauth_capture_store_backend": "file",

  "credential_providers": {
    "codex": {
      "type": "oauth_capture",
      "token_endpoints": [
        {
          "host": "https://auth.openai.com",
          "path": "/oauth/token",
          "response_fields": [
            { "path": "access_token",  "kind": "opaque" },
            { "path": "refresh_token", "kind": "opaque" }
          ]
        }
      ]
    }
  }
}
```

Persists to `~/.local/state/nono/oauth-capture/providers.json` (`0600`, parent
directory `0700`), on every platform including macOS.

### Errors

If the Keychain backend is selected but the login keychain is locked or
otherwise not writable (SSH session, post-sleep without a GUI unlock, or a
lock-on-inactivity policy), capture **fails closed** — it does not fall back to
a file or to memory. The write path surfaces:

```
OAuth capture keystore error: OAuth capture store save for nono/oauth_capture_store blocked: keychain is locked (OSStatus -25308). Common causes: SSH session, post-sleep without GUI unlock, or Keychain Access set to lock on inactivity. OAuth capture fails closed and is unavailable until the login keychain is unlocked; there is no in-memory fallback.
```

`OSStatus -25308` is `errSecInteractionNotAllowed`; you may also see `-25293`
(`errSecAuthFailed`) or `-25304` (`errSecNotAvailable`), all reported
identically. Unlock the login keychain, or switch to Option B.

If you enable the Keychain backend but omit the `security` command policy,
profile resolution refuses to start rather than silently breaking the agent's
`security` calls:

```
profile enables OAuth-capture Keychain persistence on macOS but does not define a command_policies.commands."security" policy with a session sandbox. Define command_policies.commands."security".sandbox (or .from.session) so the agent's other `security` calls keep working while reads of account 'oauth_capture_store' are refused, or set oauth_capture_store_backend = "file" to opt out of the Keychain backend.
```

## Claude Code

Login capture:

```sh
RUST_LOG=nono_proxy::oauth_capture=debug,nono_proxy::tls_intercept=debug \
target/debug/nono run \
  --profile claude-oauth-login \
  --allow-cwd \
  --allow-launch-services \
  -- claude auth login
```

Expected evidence:

- `configured OAuth capture endpoint provider=claude_code`
- `matched OAuth capture endpoint provider=claude_code`
- `rewrote OAuth token response fields to phantoms`
- `Login successful.`

Use run mode without launch-services after login:

```sh
RUST_LOG=nono_proxy::oauth_capture=debug,nono_proxy::tls_intercept=debug \
target/debug/nono run \
  --profile claude-oauth \
  --allow-cwd \
  -- claude -p --no-session-persistence "reply with ok"
```

Expected evidence:

- `loaded persisted OAuth phantom mappings`
- `resolved OAuth phantom token for admitted consumer`
- the command succeeds without granting raw Keychain access

## Codex

Device-code login:

```sh
RUST_LOG=nono_proxy::oauth_capture=debug,nono_proxy::tls_intercept=debug \
target/debug/nono run \
  --profile codex-oauth-login \
  --allow-cwd \
  -- codex login --device-auth
```

Expected evidence:

- `/api/accounts/deviceauth/token` is matched during polling
- `/oauth/token` is matched during token exchange
- `rewrote OAuth token response fields to phantoms`
- `Successfully logged in`

Check stored auth shape without printing values:

```sh
jq 'paths(scalars) as $p
  | select(($p|join("."))|test("token|auth|id"; "i"))
  | {path:($p|join(".")), type:(getpath($p)|type)}' "$CODEX_HOME/auth.json"
```

Expected evidence:

- access and refresh token fields exist as strings
- ID token, if present, is JWT-shaped synthetic content
- no real token material is printed

Run mode:

```sh
RUST_LOG=nono_proxy::oauth_capture=debug,nono_proxy::tls_intercept=debug \
target/debug/nono run \
  --profile codex-oauth \
  --allow-cwd \
  -- codex exec "reply with ok"
```

Expected evidence:

- `loaded persisted OAuth phantom mappings`
- `resolved OAuth phantom token for admitted consumer`
- the command succeeds through the authenticated session
