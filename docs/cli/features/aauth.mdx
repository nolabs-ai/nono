---
title: aauth Agent Identity
description: Sign outbound requests with a persistent keypair instead of injecting a bearer credential — pseudonymous by default, with an optional discoverable identity.
---

nono integrates with the [aauth protocol](https://github.com/dickhardt/AAuth) to authenticate
outbound API calls by signing them (RFC 9421 HTTP Message Signatures) with a persistent Ed25519
keypair, instead of injecting a bearer token. There is no secret to fetch, cache, or rotate at
request time — the request's own signature *is* the credential. The sandboxed process makes a
plain HTTP request and never sees the signing key.

Two signing schemes are supported, at two different trust levels:

- **`hwk`** — pseudonymous, zero setup. The public key travels inline in the request.
- **`jwks_uri`** — a durable, discoverable identity. The upstream resolves your public key by
  fetching a JSON document you host.

Both use the exact same keypair and the exact same signature mechanics — switching between them
is a one-field config change, not a different credential type.

---

## Getting a keypair

The recommended location for keys is **`~/.config/nono/aauth-keys/`**. You can generate a new
key there or keep an existing key elsewhere and reference its full absolute path.

Profiles read an existing **unencrypted Ed25519 PKCS#8 PEM or DER** file directly; there is no
upload or registration step:

```json
{
  "network": {
    "aauth_identity": { "key_ref": "/home/alice/.config/nono/aauth-keys/agent.pem" }
  }
}
```

An absolute filesystem path and `file:///absolute/path` mean the same thing. nono reads the
existing file in place without modifying or copying it. Relative paths are rejected. Keys must
be regular files owned by the invoking user, with no group/other permissions (`0600` or `0400`);
symlink key files are rejected. PEM files encrypted with a password, SSH key files, and non-Ed25519
keys are not supported.

To generate a new key instead:

```bash
nono aauth keygen --keyref "$HOME/.config/nono/aauth-keys/agent.pem"
```

This writes a private PKCS#8 PEM file with mode `0600`; new key directories use mode `0700`.
Creation refuses existing files atomically. `--force` replaces the destination file atomically
without truncating other hard links to the old key. Neither mode follows a destination symlink.
The destination directory must be owned by the invoking user and not writable by group/others.

To use a key stored elsewhere, set `key_ref` to its absolute path, for example
`/secure/agent-keys/agent.pem`. nono reads that file in place and does not move or copy it.
Use the full path in JSON: `~` and `$HOME` are shell conveniences and are not expanded in `key_ref`.

Existing base64-encoded PKCS#8 DER keys remain supported. Runtime `keyring://` and `env://`
references accept PEM or base64 DER values; keygen writes only to filesystem paths.
File-backed keys are not encrypted at rest. Use a trusted host location or provision an OS-keyring
entry when filesystem permissions alone do not meet your storage requirements.

Check what you have at any time:

```bash
nono aauth show --keyref "$HOME/.config/nono/aauth-keys/agent.pem"
```

This prints the algorithm, JWK thumbprint, and public JWK — never the private key.

Keep the key file **outside** any path the sandboxed process will be granted (`--allow`,
`--read`, `--write`, or a profile's filesystem capabilities). nono rejects a `file://` key
whose canonicalized path falls under a granted capability before the sandbox starts — this includes
`/tmp` on macOS, since the default sandbox policy grants broad read access to `/private` (and
`/tmp` resolves into it). A location like `~/.config/nono/aauth-keys/` works well.

## `hwk` — pseudonymous, no hosting required

Add an `aauth_identity` block and set `aauth: true` on the route that should sign:

```json
{
  "network": {
    "credentials": ["myapi"],
    "aauth_identity": {
      "key_ref": "file:///path/to/key.pem"
    },
    "custom_credentials": {
      "myapi": {
        "upstream": "https://api.internal.example.com",
        "aauth": true
      }
    }
  }
}
```

Note the credential name — `custom_credentials.<name>` becomes the `<NAME>_BASE_URL` environment
variable inside the sandbox, and hyphens in `<name>` are preserved literally, producing an env var
name (`MY-API_BASE_URL`) that isn't a valid shell identifier. Stick to hyphen-free names like
`myapi`.

That's the whole setup. The upstream verifies the signature against the public key carried inline
in the request — no discovery, no prior relationship. The tradeoff: the upstream learns "a request
from whoever holds this key," not a resolvable identity.

## `jwks_uri` — a discoverable identity

Instead of shipping the public key with every request, you publish it once at a URL and the
request carries a pointer to it. Getting there:

**1. Get the JWKS document to host:**

```bash
nono aauth show --keyref "$HOME/.config/nono/aauth-keys/agent.pem" --jwks > jwks.json
```

This prints the exact JSON to serve — `{"keys": [...]}` — with `kid` set to the key's JWK
thumbprint. It works with keys generated by nono and with existing keys referenced directly.

**2. Publish it.** Host `jwks.json` at a URL under your control (an S3 bucket, GitHub Pages,
Cloudflare Pages — it's just a static file, no server logic needed), and publish a two-line
metadata document at `https://<your-domain>/.well-known/aauth-agent.json`:

```json
{
  "issuer": "https://<your-domain>",
  "jwks_uri": "https://<your-domain>/path/to/jwks.json"
}
```

**3. Point the profile at your issuer:**

```json
{
  "network": {
    "credentials": ["myapi"],
    "aauth_identity": {
      "key_ref": "file:///path/to/key.pem",
      "scheme": { "type": "jwks_uri", "issuer": "https://<your-domain>" }
    },
    "custom_credentials": {
      "myapi": {
        "upstream": "https://api.internal.example.com",
        "aauth": true
      }
    }
  }
}
```

`issuer` must be a bare HTTPS origin — no port, no path (e.g. `https://agent.example.com`, not
`https://agent.example.com:8443/agents`). nono validates this at profile-load time.

The upstream now fetches `{issuer}/.well-known/aauth-agent.json` → reads `jwks_uri` → fetches that
→ finds the key by `kid` → verifies. This is what lets a resource report back a real identity
(the issuer itself) instead of an anonymous key — but it only works once that document is actually
reachable at that URL.

Don't set `agent_id` under `jwks_uri` — nono rejects it. The protocol has no identity finer than
the issuer at this scheme, so `agent_id` is always the issuer; setting it independently would just
be a second copy of the same fact that could silently drift from what the upstream actually sees.
Under `hwk`, `agent_id` is optional and defaults to the key's thumbprint — it's purely a label for
your own audit log, never part of the signature.

## Signing all outbound requests by default

Instead of setting `aauth: true` on every route, flip the profile-wide default and opt specific
routes out:

```json
{
  "network": {
    "credentials": ["internalapi", "legacyapi"],
    "aauth_sign_all_outbound": true,
    "aauth_identity": { "key_ref": "file:///path/to/key.pem" },
    "custom_credentials": {
      "internalapi": { "upstream": "https://api.internal.example.com" },
      "legacyapi": {
        "upstream": "https://legacy.example.com",
        "credential_key": "op://vault/legacy/token",
        "aauth": false
      }
    }
  }
}
```

`custom_credentials` entries are route *definitions* — each name must also be listed in
`network.credentials` to actually be enabled, same as any other credential.

The default only ever applies to a route that has no other auth mechanism configured — a route
that already sets `credential_key`/`oauth2`/`aws_auth`/`spiffe` or redeems caller phantoms keeps
using that, regardless of `aauth_sign_all_outbound`. Explicit `aauth: true` is mutually exclusive
with those mechanisms, including a non-empty `redeem_phantoms` list.

## Options reference

### `aauth_identity` (profile-level, one per profile)

| Field | Description |
|---|---|
| `key_ref` | Existing key: an absolute filesystem path, `file://`, `keyring://`, or `env://`. Files accept Ed25519 PKCS#8 PEM, DER, or legacy base64 DER. |
| `agent_id` | Optional local audit-log label. Under `hwk`, defaults to the key's thumbprint. Must be omitted under `jwks_uri`. |
| `scheme` | `{"type": "hwk"}` (default) or `{"type": "jwks_uri", "issuer": "https://..."}` |

### `custom_credentials.<name>` (per route)

| Field | Description |
|---|---|
| `aauth` | `true` to sign this route, `false` to opt out of `aauth_sign_all_outbound`. Mutually exclusive with `credential_key`, `auth`, `aws_auth`, `spiffe`. |

## Inspecting the audit log

Every aauth-signed request is recorded in the session's audit trail like any other network call —
find the session and inspect it:

```bash
nono audit list --json
nono audit show <session-id> --json
```

The network event for a signed call carries an `aauth_context` block alongside the usual
`auth_mechanism`/`auth_outcome` fields:

```json
{
  "auth_mechanism": "aauth_signature",
  "auth_outcome": "succeeded",
  "injection_mode": "aauth_signature",
  "aauth_context": {
    "scheme": "hwk",
    "key_thumbprint": "jZlTVONSpz7TLBqT-OLUr2pcSs1JgByUZqAjKV5e3Ic"
  },
  "target": "myapi",
  "method": "GET",
  "path": "/widgets",
  "status": 200
}
```

`agent_id` only appears if the profile set one. Under `jwks_uri`, `agent_id` and `issuer` are
always present and equal to the issuer URL.

## What nono handles

- Signing every request that opts in — method, path, authority, and the request body (via
  `Content-Digest`) whenever one is present, so a body swapped in flight is rejected, not silently
  accepted
- Building the correct `Signature-Key` for whichever scheme is configured
- Keeping the signing key isolated from the sandboxed process — a `file://` key under any path the
  sandboxed process is granted is rejected before the sandbox starts, and an `env://` key's value is
  stripped from the sandboxed child's environment even though nono passes through the rest of the
  parent environment by default
- Zeroing key material on drop

## What you handle

- Providing an existing key file directly, or generating a dedicated agent key
- For `jwks_uri`: hosting the JWKS document and the `aauth-agent.json` metadata document somewhere
  reachable over HTTPS — nono never hosts this itself, since it runs as a short-lived local sandbox
  process, not a persistent public service

## Signing authority, replay protection, and rotation

The proxy signs calls permitted by the selected route. A signature establishes key possession;
it does not imply a human approved the action or authorize the caller to use every endpoint.
Use dedicated agent keys and narrow `endpoint_policy` rules for sensitive APIs.

Every signature covers the method, authority, path, non-empty query, and a SHA-256 Content-Digest,
including an empty-body digest. Content-Type, Content-Encoding, Idempotency-Key, and Aauth-Mission
are covered when present. Duplicate semantic headers are rejected. Receivers must require every
component their application relies on and reject missing or altered covered components.

Each request has a fresh cryptographically random signed `nonce`, a signed `created` timestamp,
and a signed `expires` timestamp 60 seconds later. **The receiving service must validate expiry
and atomically reject repeated nonces for the same key**, retaining them through the accepted
clock-skew window. These fields enable replay prevention; adding a nonce alone does not reject
replays. Keep HTTPS enabled outside the explicitly supported loopback test case.

For `hwk`, the service must decide which public keys are authorized. A valid signature from an
unknown key is not an enrolled user identity. For `jwks_uri`, the service must enforce issuer
trust and safe HTTPS metadata/JWKS discovery; nono does not turn arbitrary issuers into trusted
users. Discovery clients should restrict egress and redirects and validate the expected issuer.

The proxy loads its key at startup. To rotate a `jwks_uri` key, publish the new public key alongside
the old key with its new thumbprint `kid`, update the private-key reference, and restart affected
sessions. Retire the old public key according to your service's session and replay policy. For
`hwk`, enroll the new public-key thumbprint at the resource before switching keys. Revocation and
permissions remain the receiving service's responsibility.

## What's not supported yet

aauth defines five `Signature-Key` schemes; nono currently signs with two of them, `hwk` and
`jwks_uri`. Not supported:

- **`jwt` / `jkt-jwt`** — token-based identity, where the agent exchanges a resource-issued token
  with an authorization server (and possibly a human, via a person server) before signing with it.
  This needs a 401-challenge/token-exchange flow that doesn't exist yet — it's a bigger feature
  than a signing-scheme addition, since it involves a second (and possibly third) party in the
  protocol, not just nono.
- **`x509`** — certificate-based identity. Unimplemented in the underlying signing library itself,
  not just in nono.
