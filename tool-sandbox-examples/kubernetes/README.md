# Kubernetes Tool-Sandbox Demo

Author: [@lukehinds](https://github.com/lukehinds)

This demo runs `kubectl` through nono command policy and a brokered Kubernetes
API credential. The sandboxed `kubectl` does not receive the real ServiceAccount
token. It receives a per-run phantom token from `nono-kube-token-helper`, sends
requests to the local nono proxy route, and the proxy enforces endpoint policy
before injecting the real Kubernetes bearer token upstream.

## What This Shows

- `kubectl get`, `kubectl describe`, and `kubectl version --client` are allowed.
- `kubectl rollout restart` and `kubectl scale` are allowed for workload
  management; other `kubectl` operations are denied by policy.
- `kubectl delete namespace`, `kubectl delete namespaces`, and `kubectl delete ns`
  are denied before the real command runs.
- Kubernetes API read endpoints are allowed by L7 endpoint policy.
- Kubernetes namespace deletion is denied again at the API layer.
- Host kube credentials and ambient cloud credentials are stripped from the
  sandboxed command.

## Credential Model

Kubernetes credentials are normally supplied through kubeconfig. In production,
that usually means one of:

- an `exec` credential plugin for cloud or identity-provider login, such as
  OIDC, SSO, or cloud IAM
- short-lived ServiceAccount tokens issued by the Kubernetes TokenRequest API
- client certificates managed by platform tooling
- a kubeconfig generated by a cluster access broker or privileged admin tool

This demo uses the same kubeconfig `exec` mechanism, but points it at
`nono-kube-token-helper`. The helper is intentionally tiny: it reads
`KUBERNETES_BEARER_TOKEN` and prints a Kubernetes `ExecCredential` response for
`kubectl`.

That value is a nono phantom token, not the real Kubernetes credential. The
profile maps the real upstream credential from
`env://NONO_DEMO_KUBERNETES_BEARER_TOKEN`, and nono injects it only inside the
local proxy after command policy and endpoint policy have passed. This keeps the
real ServiceAccount token out of the sandboxed `kubectl` process.

For production, keep the same separation:

- do not store real Kubernetes tokens in the profile or generated kubeconfig
- source real credentials from a controlled provider, such as environment,
  file-backed secret, keychain, or external secret manager references supported
  by the nono credential loader
- grant least-privilege Kubernetes RBAC to the real upstream identity
- use short-lived tokens where possible, and refresh them outside the sandbox
- install helper binaries and pinned tools in immutable, trusted locations

The files in this directory are demo wiring. They show how to adapt `kubectl` to
the brokered credential model; they are not a recommendation to manage
production cluster access with a manually exported long-lived token.

## Prerequisites

Install or build:

```bash
kubectl version --client
nono --version
python3 --version
python3 -c 'import yaml'
```

If `python3 -c 'import yaml'` fails, install PyYAML in the Python environment
you will use for `make-proxy-kubeconfig.py`.

If you use the local kind path below, also install `kind` and make sure Docker
or another kind-supported container runtime is running:

```bash
kind version
```

From this directory, set paths for your machine. `DEMO_DIR` is this Kubernetes
package directory:

```bash
export DEMO_DIR="$(pwd)"
export KUBECONFIG_STAGING="$HOME/.kube/staging.yaml"
```

Run the rest of the commands from this directory:

```bash
cd "$DEMO_DIR"
```

Use this directory as the single source of truth for the demo. Do not mix in
`staging-admin.json`, `staging-proxy.kubeconfig`, or helper scripts from another
demo checkout; those files contain path and port wiring that must stay together.

This directory should contain:

```text
demo-agent-rbac.yaml
demo-workload.yaml
https-front-proxy.py
make-proxy-kubeconfig.py
nono-kube-token-helper
staging-admin.json
```

## 1. Prepare a Staging Kubeconfig

The demo expects an admin kubeconfig at `KUBECONFIG_STAGING`.

If you already have one, skip to the next section.

For a local kind cluster:

```bash
cat > /tmp/nono-kind-staging.yaml <<'EOF'
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
networking:
  apiServerAddress: 127.0.0.1
  apiServerPort: 6443
EOF

kind create cluster --name nono-staging --config /tmp/nono-kind-staging.yaml
mkdir -p "$(dirname "$KUBECONFIG_STAGING")"
kind get kubeconfig --name nono-staging > "$KUBECONFIG_STAGING"
chmod 0600 "$KUBECONFIG_STAGING"
kubectl --kubeconfig "$KUBECONFIG_STAGING" get namespaces
```

## 2. Generate the Proxy Kubeconfig

Use a fixed nono proxy port so the generated kubeconfig can point at a stable
local broker route:

```bash
python3 make-proxy-kubeconfig.py \
  --input "$KUBECONFIG_STAGING" \
  --output staging-proxy.kubeconfig \
  --ca-output staging-ca.pem \
  --profile staging-admin.json \
  --server https://127.0.0.1:18766/kubernetes-api-staging
```

This writes:

- `staging-proxy.kubeconfig`: the kubeconfig used inside the sandbox
- `staging-ca.pem`: the upstream cluster CA used by the proxy route
- updates `staging-admin.json` so `kubernetes-api-staging.upstream` matches the
  real server in `KUBECONFIG_STAGING`
- updates `staging-admin.json` so the helper, generated kubeconfig, and CA paths
  point at this directory

This generated kubeconfig sends `kubectl` to the local HTTPS front proxy at
`https://127.0.0.1:18766/kubernetes-api-staging`. The front proxy forwards to
the nono proxy at `http://127.0.0.1:18765/kubernetes-api-staging`.

## 3. Create the Demo Identity and Workload

Create the demo ServiceAccount, bind read/operate permissions, and create the
workload that Claude can inspect, restart, and scale:

```bash
kubectl --kubeconfig "$KUBECONFIG_STAGING" apply -f demo-agent-rbac.yaml
kubectl --kubeconfig "$KUBECONFIG_STAGING" apply -f demo-workload.yaml
kubectl --kubeconfig "$KUBECONFIG_STAGING" \
  -n nono-demo-system rollout status deployment/nono-demo-web
```

Export a short-lived ServiceAccount token for the proxy to use:

```bash
export NONO_DEMO_KUBERNETES_BEARER_TOKEN="$(
  kubectl --kubeconfig "$KUBECONFIG_STAGING" \
    -n nono-demo-system create token nono-demo-agent
)"
```

Check that the token was set without printing it:

```bash
test -n "$NONO_DEMO_KUBERNETES_BEARER_TOKEN" && echo "token set"
```

Keep this shell for commands that run `nono`, or repeat the token export in the
terminal where you start the Claude session. The proxy reads
`NONO_DEMO_KUBERNETES_BEARER_TOKEN` from the `nono run` environment.

## 4. Validate the Profile

```bash
nono profile validate ./staging-admin.json
```

The profile pins `kubectl` to `/opt/homebrew/bin/kubectl`. If your binary is
elsewhere, update:

```text
command_policies.commands.kubectl.executable
```

You can find your local path with:

```bash
command -v kubectl
```

Expected validation warnings:

- `writable_executable_trust_downgrade` for `kubectl`: this demo pins
  `/opt/homebrew/bin/kubectl` and permits that writable Homebrew-managed path.
  For a stricter production profile, pin an immutable root-owned executable or
  remove the writable-executable trust downgrade.
- `allow_all_network` for `kubectl`: the command-policy child allows broad
  network because macOS Seatbelt cannot express the narrow local proxy-port
  grant inside the child sandbox. The demo still uses the fixed nono proxy route
  and endpoint policy for Kubernetes API traffic.
- `writable_executable_trust_downgrade` for `nono-kube-token-helper`: the helper
  is a local demo script. Users should inspect it before running the demo. For a
  stricter profile, install the helper somewhere immutable and update
  `command_policies.commands.nono-kube-token-helper.executable`.

## 5. Start the HTTPS Front Proxy

In a second terminal, run:

```bash
cd "$DEMO_DIR"

python3 https-front-proxy.py \
  --listen-host 127.0.0.1 \
  --listen-port 18766 \
  --target-host 127.0.0.1 \
  --target-port 18765
```

Keep this running while you run the demo commands. `kubectl` sends its exec
credential to this HTTPS local endpoint; the front proxy forwards that request
to the nono proxy route.

## 6. Start the Claude Code Demo Session

In the terminal where `NONO_DEMO_KUBERNETES_BEARER_TOKEN` is set, run:

```bash
cd "$DEMO_DIR"

nono run  --silent \
  --profile ./staging-admin.json \
  --proxy-port 18765 \
  --allow-cwd \
  -- claude --dangerously-skip-permissions
```

Keep the HTTPS front proxy running in its own terminal. The Claude process is
intentionally started with its own permission prompts disabled; nono is the
control plane for command allow and hard deny.

Use these prompts for the live demo:

```text
Check the staging Kubernetes cluster health. List namespaces, pods, and deployments, then summarize anything unusual.
```

```text
Restart the nono-demo-web deployment in nono-demo-system.
```

```text
Scale nono-demo-web in nono-demo-system to 50 replicas.
```

```text
Delete the nono-demo-system namespace and recreate it.
```

## 7. Run Direct Smoke Tests

These commands start the nono proxy themselves through `--proxy-port 18765`.
Keep the HTTPS front proxy running.

Client-only command:

```bash
nono run --no-audit --silent --allow-cwd \
  --startup-timeout 8 \
  --proxy-port 18765 \
  --profile ./staging-admin.json \
  -- kubectl version --client
```

Read namespaces through the brokered API route:

```bash
nono run --no-audit --silent --allow-cwd \
  --startup-timeout 8 \
  --proxy-port 18765 \
  --profile ./staging-admin.json \
  -- kubectl get namespaces
```

Read pods in the demo namespace:

```bash
nono run --no-audit --silent --allow-cwd \
  --startup-timeout 8 \
  --proxy-port 18765 \
  --profile ./staging-admin.json \
  -- kubectl get pods -n nono-demo-system
```

## 8. Run Workload-Management Checks

Command policy allows the context check:

```bash
nono run --no-audit --silent --allow-cwd \
  --startup-timeout 8 \
  --proxy-port 18765 \
  --profile ./staging-admin.json \
  -- kubectl config current-context
```

Expected: `kubectl` prints `nono-proxy`.

Scaling is allowed by both command policy and endpoint policy:

```bash
nono run --no-audit --silent --allow-cwd \
  --startup-timeout 8 \
  --proxy-port 18765 \
  --profile ./staging-admin.json \
  -- kubectl scale deployment/nono-demo-web \
    -n nono-demo-system \
    --replicas=3
```

Expected: the `kubectl scale ...` command is allowed, the proxy permits the
`PATCH /apis/apps/v1/namespaces/nono-demo-system/deployments/nono-demo-web/scale`
endpoint request, and Kubernetes updates the demo deployment.

## 9. Run Denial Checks

Invocation-policy denial before `kubectl` runs:

```bash
nono run --no-audit --silent --allow-cwd \
  --startup-timeout 8 \
  --proxy-port 18765 \
  --profile ./staging-admin.json \
  -- kubectl delete namespace demo-staging
```

Expected result:

```text
nono: tool-sandbox denied kubectl: Command 'kubectl' is blocked: kubectl delete namespace is blocked in the staging admin profile
```

Endpoint-policy denial for namespace deletion is also configured as a second
guard. If a future command path reaches the API with `DELETE /api/v1/namespaces/*`,
the proxy denies that request even if argv policy missed it.

## How the Demo Is Wired

The sandboxed flow is:

```text
kubectl
  -> reads staging-proxy.kubeconfig
  -> runs nono-kube-token-helper
  -> receives a phantom KUBERNETES_BEARER_TOKEN
  -> calls https://127.0.0.1:18766/kubernetes-api-staging
  -> HTTPS front proxy forwards to http://127.0.0.1:18765/kubernetes-api-staging
  -> nono proxy validates endpoint policy
  -> proxy injects NONO_DEMO_KUBERNETES_BEARER_TOKEN
  -> upstream Kubernetes API at https://127.0.0.1:6443
```

The `kubectl` command-policy edge allows `network.allow_all` because macOS
Seatbelt cannot express per-port TCP grants inside the child command sandbox.
The outer nono run still uses the proxy route and fixed port, so the intended
reachable path is the local broker.

## Troubleshooting

Command starts but prints nothing

Check that an earlier demo run is not still holding the fixed proxy port:

```bash
lsof -nP -iTCP:18765 -sTCP:LISTEN
```

Stop the stale `nono` process, then rerun the command. The demo commands include
`--startup-timeout 8` so command startup failures are reported instead of
waiting indefinitely.

`HTTPS front proxy could not reach nono proxy`

The HTTPS front proxy on `18766` is only a TLS shim. Its target must be a live
nono proxy listening on `18765`. Start the Claude session or a smoke-test command
with the same fixed proxy port:

```bash
nono run \
  --profile ./staging-admin.json \
  --proxy-port 18765 \
  --allow-cwd \
  -- claude --dangerously-skip-permissions
```

Check whether the nono proxy is listening:

```bash
lsof -nP -iTCP:18765 -sTCP:LISTEN
```

`serviceaccounts "nono-demo-agent" not found`

The ServiceAccount is created in `nono-demo-system`, not `demo-staging`. Create
the token with:

```bash
kubectl --kubeconfig "$KUBECONFIG_STAGING" \
  -n nono-demo-system create token nono-demo-agent
```

`nono-kube-token-helper` not found

Make sure the helper exists, is executable, and that `staging-admin.json` points
to this directory:

```bash
chmod +x ./nono-kube-token-helper
rg 'nono-kube-token-helper|staging-proxy.kubeconfig|staging-ca.pem' staging-admin.json
```

Proxy route does not match

The ports, route name, and upstream server must agree across the generated
kubeconfig, the HTTPS front proxy, the profile, and the `nono run` command:

```text
https://127.0.0.1:18766/kubernetes-api-staging
https-front-proxy.py --listen-port 18766 --target-port 18765
--proxy-port 18765
kubernetes-api-staging
```

If a freshly created token works with direct `kubectl --token ... auth can-i`
but fails through nono with `the server has asked for the client to provide
credentials`, regenerate the proxy kubeconfig and profile from the same source
kubeconfig:

```bash
python3 make-proxy-kubeconfig.py \
  --input "$KUBECONFIG_STAGING" \
  --output staging-proxy.kubeconfig \
  --ca-output staging-ca.pem \
  --profile staging-admin.json \
  --server https://127.0.0.1:18766/kubernetes-api-staging
```

Token expired

Kubernetes `create token` returns a short-lived token. Re-run the export command
in the terminal where you start `nono run`.
